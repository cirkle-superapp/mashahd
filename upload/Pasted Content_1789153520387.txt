# MASTER IMPLEMENTATION PROMPT

## Zero-Cost Hybrid CDN + WebRTC P2P Video Streaming Platform

You are the Principal Full-Stack Architect, Video Streaming Engineer, WebRTC Engineer, Distributed Systems Engineer, Security Engineer, DevOps Engineer, Performance Engineer, QA Engineer, and Production Readiness Engineer for this project.

Your task is to implement a **production-grade, YouTube-like video streaming infrastructure** whose primary objective is:

> **Minimize the operator's recurring infrastructure cost to effectively zero by using self-hosted/open-source infrastructure and opportunistic WebRTC peer-to-peer delivery for eligible users, while preserving CDN/origin delivery as the authoritative fallback.**

Do not build this as a toy demo.

Do not create disconnected examples.

Do not replace working architecture unnecessarily.

Do not introduce paid cloud services or subscription-dependent infrastructure.

The final implementation must be integrated, wired end-to-end, tested, observable, secure, resilient, and capable of being run entirely on self-controlled infrastructure.

---

# 1. NON-NEGOTIABLE OPERATING PRINCIPLE

The architecture MUST follow this rule:

```text
ORIGIN / CDN = AUTHORITATIVE SOURCE
P2P         = DELIVERY OPTIMIZATION / CACHE ACCELERATOR
```

P2P must NEVER become a mandatory dependency for playback.

If P2P fails, is unavailable, is slow, has insufficient peers, encounters NAT restrictions, or violates a device/network policy:

```text
PLAYBACK MUST CONTINUE THROUGH NORMAL HTTP/HTTPS DELIVERY.
```

There must be:

```text
NO STALL
NO DEADLOCK
NO REQUIRED P2P
NO REQUIRED TURN RELAY
NO DATA LOSS
NO USER-FACING P2P ERROR
```

# 8. SWARM ID ARCHITECTURE

Every compatible representation must have a deterministic swarm.

Do NOT simply use a human-readable URL as the sole swarm identifier.

Generate:

```text
swarmId =
sha256(
  videoId +
  renditionId +
  manifestVersion
)
```

Examples:

```text
video123:1080p:v1
video123:720p:v1
video123:480p:v1
video123:360p:v1
```

This prevents peers from exchanging incompatible media.

The swarm must change when:

```text
video changes
rendition changes
manifest version changes
encoding generation changes
```

The client loading exactly the same:

```text
video
+
rendition
+
manifest version
```

must automatically enter the same swarm.

# 14. P2P DOWNLOAD STRATEGY

For each segment request:

```text
1. Determine whether segment is available from peers.
2. Request from eligible P2P peer(s).
3. Keep HTTP fallback available.
4. If peer delivery is slower than configured threshold:
       cancel/ignore the peer request
       retrieve via HTTP.
5. If peer is unavailable:
       HTTP immediately.
6. Verify received data.
7. Feed valid media into the normal HLS/MSE pipeline.
```

The player must never wait indefinitely for P2P.

Use bounded timeouts.
